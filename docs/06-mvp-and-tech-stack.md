# 06. MVP 범위 · 기술 스택

01~05의 기획을 바탕으로 **처음 만들 범위(MVP)**, 개발 순서, 기술 스택, 배포 방식을 정합니다. 이 문서부터는 실제 구현을 위한 결정입니다.

---

## 결정 기준

이 프로젝트의 성격에서 나온 기준입니다.

1. **클론한 운영자가 쉽게 띄울 수 있어야 함**: Code-Name-JS는 직접 배포하지 않고, 저장소를 가져간 운영자가 배포합니다(01 [배포와 운영](./01-service-definition.md#배포와-운영에-관한-안내)). 명령 몇 줄로 띄울 수 있어야 합니다.
2. **사건 하나, 짧은 수명**: 사이트는 사건 1건만 다루고 몇 달 안에 폐쇄됩니다. 대규모 확장보다 **단순함과 낮은 비용**이 중요합니다.
3. **깔끔하게 내릴 수 있어야 함**: 폐쇄 후 5일 안에 개인정보를 파기해야 합니다(05). 데이터가 여러 외부 서비스에 흩어지지 않을수록 좋습니다.
4. **서버가 꼭 필요함**: IP 하나에 계정 하나 규칙, 평결 익명성, 워터마크, 단계 자동 전환은 모두 서버에서 처리해야 합니다. 정적 사이트만으로는 만들 수 없습니다.
5. **JavaScript 생태계**: 제작자가 HTML, CSS, JavaScript로 공부해 온 만큼 같은 언어로 화면과 서버를 모두 만듭니다.

---

## MVP 범위

**MVP = 1심 한 바퀴 + 사이트 폐쇄.** 사건 게시부터 공소 투표, 서명, 진영 게시판, 최종 변론, 평결, 판결을 거쳐 사이트 폐쇄까지 한 사이트의 일생을 처음부터 끝까지 돌릴 수 있는 최소 범위입니다.

MVP로 연 사이트에서는 리뷰와 2심 없이 **1심 판결이 곧 확정**되고, 사이트가 폐쇄됩니다.

> **MVP는 테스트 기간입니다.** MVP 버전에서는 01에서 약속한 항소(리뷰)와 2심이 동작하지 않고, 만 14세 미만 가입도 막혀 있습니다. 그래서 MVP 버전의 사이트는 **테스트용으로만** 쓰고, 실제 사건 운영은 리뷰·2심·법정대리인 동의가 들어간 **2차 완성 버전**으로 하기를 권합니다.

### MVP에 넣는 것

03의 화면 ID 기준입니다.

| 영역 | 화면 |
|---|---|
| 공개 | H-01 홈, A-01 프로젝트 소개, A-02 재판 진행 과정, A-03 참여 가이드, N-01 공지사항, L-01 이용약관, L-02 개인정보처리방침, **X-01 종료 안내 페이지** |
| 회원 | U-01 로그인, U-02 회원가입, U-03 내 활동, U-04 알림, U-05 제재 내역·이의 신청, **U-07 IP 변경 인증** |
| 사건 | C-01 사건 페이지, C-02 공소 투표, C-03 투표 결과, C-04 공판준비 서명, C-05 진영 게시판, C-06 스레드, C-07 최종 변론인 선정, C-08 최종 변론, C-09 평결, C-10 판결 결과 |
| 관리자 | O-01 대시보드, O-02 사건 생성·검수, O-03 사건 관리, O-05 신고·제재(수동), O-06 공지 관리, O-07 회원 관리(IP 기록), **O-08 사이트 폐쇄** |

| 기능 | MVP 수준 |
|---|---|
| 단계 자동 전환 | 1분마다 마감을 확인해 다음 상태로 넘김. 인원 미달 자동 폐기 포함 |
| IP 하나에 계정 하나 | 가입·로그인·요청마다 확인, IP 변경 이메일 인증(하루 5회) |
| 워터마크 | 게시판 화면 위에 열람자 닉네임과 코드를 옅게 반복 표시, `view_log` 기록 |
| 유출 대응 | 신고 → 운영자 확인 → 수동 제재. 자동 탐지는 2차 |
| 평결 | 참여 여부와 투표 내용을 분리 저장(04) |
| AI | 최종 변론인 AI 추천만 AI API로 호출([AI 연동](#ai-연동) 참고) |
| 알림 | 화면 안 알림 + 꼭 필요한 이메일(인증 코드, 서명 요청, 평결 요청, 변론인 선정, 폐쇄 예고) |
| 폐쇄 | 종료 안내 페이지 전환, 개인정보 파기 스크립트 |
| 보안 | 비밀번호 해시(argon2id), 세션 쿠키, 요청 위조(CSRF) 방지, 요청 횟수 제한, 관리자 2단계 인증 |

### 2차로 미루는 것

| 기능 | 이유 |
|---|---|
| C-11 리뷰, C-12 2심 참여, O-04 2심 신청 승인, 2심 진행 전체 | 1심 한 바퀴가 먼저 안정되어야 함. 2심은 1심 흐름을 다시 쓰는 구조라 1심 완성 후 붙이기 쉬움 |
| U-08 법정대리인 동의 | 절차와 법률 검토가 필요함. **MVP 기간은 테스트 기간이므로 만 14세 미만 가입을 막아 두고**, 2차에 동의 절차를 열어 05 결정을 완성 |
| 자동 유출 탐지 (복사 글, 비정상 열람, 보이지 않는 텍스트 지문) | 신고와 수동 확인으로 먼저 운영해 보고 필요한 수준을 정함 |
| U-06 배지, A-04 FAQ, L-03 문의하기 | 핵심 흐름이 아님 |
| AI 사건 생성 API 연동 | MVP에서는 운영자가 AI 플랫폼에서 받은 원본과 직접 정리한 정리본을 입력함 |

## 기술 스택

> **기술 스택은 배포하는 사람이 자유롭게 정합니다.** Code-Name-JS는 AI 플랫폼을 활용해 이 서비스의 기획을 시도했으며, 기술 스택에 대한 기초지식은 없습니다. 아래는 기획 과정에서 정리한 **추천안일 뿐**이며, 이 저장소를 클론해 배포하려는 사람은 자신의 판단과 권한으로 어떤 기술 스택이든 사용할 수 있습니다(01 [기술 스택은 배포하는 사람이 자유롭게 정합니다](./01-service-definition.md#기술-스택은-배포하는-사람이-자유롭게-정합니다)).

### 추천안

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | **TypeScript** | JavaScript와 같은 문법에 타입 검사를 더해, 상태 15개·권한 규칙처럼 복잡한 로직의 실수를 줄임 |
| 웹 프레임워크 | **Next.js** (App Router) | 화면과 서버 API를 한 프로젝트에서 만듦. 자료와 배포 사례가 가장 많아 클론한 운영자가 도움을 받기 쉬움 |
| 데이터베이스 | **PostgreSQL** | 04의 유일 조건·관계를 그대로 표현할 수 있는 관계형 DB. 무료로 쓸 수 있고 어디서나 띄울 수 있음 |
| DB 도구 | **Prisma** | 04 데이터 모델을 스키마 파일 하나로 관리하고, 마이그레이션을 자동으로 만듦 |
| 화면 스타일 | **Tailwind CSS** | 시안의 색과 간격을 설정값으로 관리. CSS 파일을 따로 키우지 않음 |
| 단계 자동 전환 | **별도 워커 프로세스** (1분마다 실행) | 외부 예약 서비스 없이 같은 서버 안에서 마감 처리 |
| 이메일 | **SMTP** (nodemailer) | 특정 업체에 묶이지 않음. 운영자가 쓰는 메일 서비스의 SMTP 정보만 넣으면 됨 |
| 이미지 저장 | **서버 디스크** (MVP) | 이미지 5MB × 4장 제한이면 사건 1건 규모에 충분. 폐쇄 때 함께 지우기 쉬움. 필요하면 S3 호환 저장소로 바꿀 수 있게 만듦 |
| 배포 | **Docker Compose** (앱 + 워커 + DB + Caddy) | 서버 한 대에서 `docker compose up` 한 번으로 실행. Caddy가 HTTPS 인증서를 자동으로 발급 |
| 테스트 | **Vitest** (단위), **Playwright** (화면 흐름) | 상태 전환·권한 규칙은 단위 테스트로, 1심 한 바퀴는 화면 흐름 테스트로 확인 |

### 왜 서버 한 대에 Docker Compose인가

- **사건 1건 규모에 맞음**: 참여자가 수천 명이어도 서버 한 대와 PostgreSQL 하나로 충분합니다.
- **폐쇄가 간단함**: 데이터가 서버 한 대 안에만 있으므로, 폐쇄 때 DB와 이미지 폴더를 지우면 파기가 끝납니다. 여러 클라우드 서비스에 흩어져 있으면 하나씩 찾아 지워야 합니다.
- **IP 확인이 정확함**: 앞단의 Caddy 하나만 실제 접속 IP를 전달하도록 설정하면, 사용자가 IP를 속여 보내는 헤더를 무시할 수 있습니다. IP 하나에 계정 하나 규칙의 신뢰도가 여기서 결정됩니다.
- **비용이 낮음**: 월 몇천~1만 원대의 작은 서버로 운영할 수 있습니다.

### 다른 배포 방식

추천안의 코드를 그대로 쓰면서 배포 방식만 바꿀 수 있게 만듭니다.

| 방식 | 장점 | 주의할 점 |
|---|---|---|
| Vercel + 관리형 PostgreSQL (Neon, Supabase 등) | 서버 관리 없이 배포 | 워커 대신 예약 실행(cron) 기능을 써야 함. 이미지는 외부 저장소 필요. 폐쇄 때 각 서비스의 데이터를 따로 파기해야 함 |
| Railway, Fly.io 등 컨테이너 호스팅 | Docker Compose와 비슷하게 쓰면서 서버 관리 부담이 적음 | 저장 공간(볼륨) 설정 필요 |

## AI 연동

| 기능 | MVP | 방식 |
|---|---|---|
| 사건 생성 | 원본 + 정리본 입력 | 운영자가 AI 플랫폼에 사건 생성을 부탁하고, O-02 화면에 **AI 원본**과 운영자가 문제없게 고친 **정리본**을 함께 입력. 사용한 AI 모델과 생성 일시도 기록. 사건 페이지는 정리본을 기준으로 보여 주고 원본도 공개 |
| 최종 변론인 추천 | **API 호출** | 추천 투표가 마감되면 서버가 AI API를 호출해, 후보들이 쓴 글과 배심원의 추천 이유를 보내고 진영별 추천과 이유를 받음. 보낸 내용과 받은 답을 기록하고 추천과 이유를 공개. **최종 선정은 운영자가 단 한 번** 함 (O-03) |

- AI 제공자는 정하지 않습니다. 운영자가 쓰는 AI 플랫폼의 API 주소, 키, 모델 이름을 환경 변수로 넣도록 하고, 코드에는 제공자를 바꿔 끼울 수 있는 연결부만 둡니다.
- AI가 답하지 않거나 형식이 맞지 않으면 두 번 다시 시도합니다. 그래도 실패하면 AI 추천 없이 운영자가 선정하고, 그 사실을 공개합니다.
- 운영자가 단계 마감까지 선정하지 않으면 AI 추천이 그대로 확정되고, AI 추천도 없으면 추천 표를 가장 많이 받은 후보로 확정합니다(02).
- AI에게는 후보의 닉네임과 게시글만 보내고, 이메일이나 IP 같은 개인정보는 보내지 않습니다.

## 개발 순서

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| **M0 기반** | 프로젝트 생성, Docker Compose, Prisma 스키마(04), 회원가입·로그인·이메일 인증, IP 하나에 계정 하나, 첫 운영자 계정, 관리자 2단계 인증 | 로컬에서 `docker compose up`으로 실행되고, 같은 IP로 두 번째 계정을 만들 수 없음 |
| **M1 게시 · 공소 투표** | O-02 사건 입력(AI 원본 + 정리본)·검수·기간 설정·게시와 "AI가 만든 사건" 공지, 워커의 단계 자동 전환, C-01~C-03, 인원 미달 자동 폐기 | 짧은 기간으로 설정한 사건이 게시 → 투표 → 공소 제기 대기 또는 폐기까지 자동으로 넘어감 |
| **M2 서명 · 진영 게시판** | C-04 서명, O-03 공소 제기, C-05·C-06 스레드와 증거자료, 열람 범위 제한, 워터마크, 신고, 수동 제재와 이의 신청 | 증거 제출 기간에는 상대 측 게시판이 보이지 않고, 기간이 끝나면 양측이 공개됨 |
| **M3 변론 · 평결 · 판결** | C-07 추천 투표와 AI 추천, O-03 운영자의 변론인 선정(단 한 번), C-08 최종 변론, C-09 평결(분리 저장), O-03 판결 작성, C-10 판결과 설득 지표 | 1심 한 바퀴가 끝까지 돌아가고, 평결 데이터로 개인 표를 알아낼 수 없음 |
| **M4 폐쇄 · 마무리** | O-08 폐쇄, X-01 종료 안내 페이지, 파기 스크립트, 이메일 알림, 공개 화면(A, L), 배포 안내서 | 폐쇄 후 모든 주소가 종료 안내 페이지로 가고, DB에 개인정보가 남지 않음 |
| **2차** | 리뷰, 2심, 법정대리인 동의, 자동 유출 탐지, 배지, FAQ, 문의 | |

각 단계마다 [시연 모드](#시연-모드)로 짧은 사건을 끝까지 돌려 확인합니다.

## 시연 모드

실제 기간(1심 66~89일)으로는 개발 중에 흐름을 확인할 수 없습니다. 02에서 운영자가 **게시 전에** 기간을 조정할 수 있게 했으므로, 이를 이용합니다.

- 개발·시연용 설정에서는 모든 단계 기간을 **분 단위**로 줄일 수 있게 합니다(예: 공소 투표 5분, 증거 제출 10분).
- 테스트용 계정을 여러 개 만들 때 IP 규칙에 막히지 않도록, **개발 환경에서만** IP 규칙을 끌 수 있게 합니다. 실제 배포 설정에서는 끌 수 없습니다.

`src/domain`에는 02의 상태 전환과 03의 접근 권한 규칙을 화면과 상관없는 순수한 함수로 모읍니다. 서비스의 규칙이 가장 많이 모이는 곳이라, 여기를 테스트로 단단히 지키는 것이 중요합니다.

### 환경 변수

| 이름 | 설명 |
|---|---|
| `SITE_URL` | 사이트 주소 |
| `DATABASE_URL` | PostgreSQL 연결 정보 |
| `SESSION_SECRET` | 로그인 세션 서명용 비밀 키 |
| `IP_HASH_SECRET` | IP 해시용 비밀 키 (폐쇄 때 폐기) |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` | 이메일 발송 |
| `AI_API_URL`, `AI_API_KEY`, `AI_MODEL` | 최종 변론인 추천용 AI |
| `OPERATOR_EMAIL` | 이 이메일로 가입한 계정이 첫 운영자가 됨 |
| `DEMO_MODE` | 개발·시연용. 분 단위 기간과 IP 규칙 끄기를 허용 |

## 기술적으로 주의할 점

| 항목 | 내용 |
|---|---|
| 실제 접속 IP | 사용자가 보내는 `X-Forwarded-For` 헤더는 얼마든지 속일 수 있습니다. 앞단 프록시(Caddy) 하나만 믿고, 그 프록시가 붙인 값만 읽습니다 |
| 워터마크의 한계 | 화면 위에 겹친 워터마크는 브라우저 개발자 도구로 지운 뒤 캡처할 수 있습니다. MVP에서는 억지 효과를 노리고, 2차에서 글 속에 보이지 않는 열람자별 문자 지문을 넣어 복사·붙여넣기 유출을 추적하는 방법을 검토합니다 |
| 평결 익명성 | 평결 내용 테이블에는 시각을 저장하지 않고 무작위 ID를 씁니다. 서버 로그에도 평결 내용을 남기지 않습니다 |
| 마감 시각 | 모든 마감은 서버 시각 기준으로 처리하고, 화면에는 한국 시간으로 표시합니다 |
| 동시 투표 | 마감 직전에 투표가 몰려도 1인 1표가 지켜지도록 DB의 유일 조건으로 막습니다(04) |
| 백업 | 운영 중에는 하루 1회 DB를 백업하되, 폐쇄 때 백업본도 함께 파기합니다(05) |
