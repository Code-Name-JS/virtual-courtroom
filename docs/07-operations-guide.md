# 07. 배포 · 운영 안내서

이 저장소를 가져가 사이트를 열고, 사건 하나를 진행하고, 사이트를 폐쇄할 때까지 운영자가 할 일을 순서대로 정리합니다. 기술 스택은 [06](./06-mvp-and-tech-stack.md)의 추천안 기준이며, 배포하는 사람이 자유롭게 바꿀 수 있습니다.

> M6까지 끝나 01에서 약속한 흐름(리뷰·2심, 만 14세 미만의 법정대리인 동의)이 모두 동작하고, M7에서 유출 자동 탐지와 증거 이미지 업로드가 더해졌습니다. 출시 전에 아래 1번의 법률 검토, 특히 **이메일로 법정대리인 동의를 받는 방법이 충분한지** 꼭 확인하세요 (05).

## 1. 출시 전에 할 일

| 할 일 | 이유 |
|---|---|
| 이용약관과 개인정보처리방침을 **법률 전문가에게 검토받고** 고친 뒤 `.env`의 `LEGAL_DOCS_REVIEWED=true` | 기본 템플릿이며, 면책·제재 조항은 법률에 따라 효력이 달라질 수 있음 (01 배포와 운영에 관한 안내) |
| `OPERATOR_NAME`, `OPERATOR_CONTACT_EMAIL`, `PRIVACY_PROCESSORS` 입력 | 개인정보처리방침에 반드시 적어야 하는 내용 (05) |
| 이메일(SMTP) 설정 | 인증 코드와 서명·평결 요청, 폐쇄 안내, 만 14세 미만의 법정대리인 동의 요청을 보냄 |
| 법정대리인 동의 방법 검토 | 이메일 링크로 동의를 받는 방법이 운영자의 상황에서 충분한지 법률 검토. 부족하면 다른 확인 방법을 더해야 함 (05) |
| AI 설정 (선택) | 최종 변론인 AI 추천. 비우면 AI 추천 없이 운영자가 선정 |
| 홍보 계획 | 공소 투표 마감 때 참여자가 최소 인원(50명)에 못 미치면 **연장 없이 바로 폐기되고 사이트가 폐쇄됨** (05 결정 6) |

## 2. 서버에 배포하기

1. Docker가 설치된 서버를 준비하고, 도메인이 서버 IP를 가리키도록 DNS를 설정합니다.
2. 저장소를 받고 `.env.example`을 `.env`로 복사해 값을 채웁니다. 비밀 키는 32자 이상의 무작위 문자열로 만듭니다.

```bash
openssl rand -hex 32
```

3. 실행합니다. 앱, 워커, DB, Caddy가 함께 뜨고 Caddy가 HTTPS 인증서를 자동으로 발급합니다.

```bash
docker compose up -d --build
```

4. 워커가 돌고 있는지 확인합니다. "단계 자동 전환 워커를 시작합니다"와 AI 설정 상태가 보여야 합니다. 워커는 비정상 열람 탐지도 맡습니다.

```bash
docker compose logs worker
```

**IP 규칙 주의:** 앱은 Caddy가 넣어 주는 `X-Real-IP`로 접속 IP를 판단합니다. Caddy 앞에 Cloudflare 같은 다른 프록시를 두면 모든 사용자가 같은 IP로 보여 가입이 막힙니다. 이때는 Caddy에 신뢰할 프록시(`trusted_proxies`)를 설정해야 합니다.

**증거 이미지:** 배심원이 올린 이미지는 `uploads` 볼륨(컨테이너 안 `/app/uploads`)에 저장됩니다. DB를 백업한다면 이 볼륨도 함께 백업하고, 폐쇄 때 함께 파기합니다. 앞단에 다른 프록시를 두면 요청 크기 제한이 22MB(이미지 5MB × 4장 + 글) 이상인지 확인하세요.

## 3. 운영자 계정

1. `OPERATOR_EMAIL`로 가입하면 운영자 계정이 됩니다. 운영자는 배심원으로 참여할 수 없습니다.
2. `/admin`에 처음 들어가면 인증 앱으로 2단계 인증을 설정합니다. 이후 로그인할 때마다 관리자 영역에 들어가기 전에 코드를 입력합니다.

## 4. 사건 진행

관리자 대시보드(`/admin`)의 "운영자의 조치가 필요한 일"을 따라가면 됩니다.

| 단계 | 운영자가 할 일 | 기한을 넘기면 |
|---|---|---|

| 공소 투표 | 기다림. 마감 시 결과를 시스템이 자동으로 판정 | — |
| 공소 제기 대기 | 공소 제기 (메모는 공개됨) | 사건 페이지에 "운영자 조치 지연" 표시 |
| 공판준비 · 증거 제출 | `/admin/reports`에서 신고와 **자동 탐지 결과**(복사 글, 비정상 열람)를 확인하고 제재하거나 기각. 워터마크 코드로 캡처·이미지를 퍼뜨린 사람을 찾을 수 있음. `/admin/members`에서 다중 계정 의심 확인 (아래 4-1) | — |
| 최종 변론인 선정 | 추천 투표(단계 앞 절반)가 끝나면 AI 추천과 배심원의 추천 이유를 보고 진영별 1명을 **단 한 번** 선정. AI 추천과 다르면 이유를 적어야 함 | AI 추천으로, AI 추천이 없으면 추천 표가 가장 많은 후보로 확정 |

| 리뷰 | 기다림. 1심 리뷰에 이의 신청이 있으면 마감 후 2심 결정으로, 없으면 확정으로 자동으로 넘어감 | — |

| 2심 재판 | 1심과 같음 (증거 제출 ~ 판결 선고). 2심 판결 뒤 리뷰가 끝나면 확정 | — |

### 4-1. 유출 탐지 결과 처리하기 (M7)

**자동 탐지 결과만으로는 제재하지 않습니다** (05). 탐지는 근거를 모아 보여 줄 뿐이고, 판단은 운영자가 합니다.

| 화면 | 보이는 것 | 할 일 |
|---|---|---|
| 신고 · 제재 (`/admin/reports`) › 자동 탐지 결과 | **복사 글**: 두 글을 나란히 두고 겹친 부분을 노란색으로 표시, 의심 글이 올라오기 전에 원본을 열람한 회원 목록 | 상대 측 정보를 옮긴 것이 맞으면 "올린 사람 제재하기"(유출 정보 게시). 정보를 전달한 사람이 워터마크·신고 등으로 확인되면 열람자 목록의 "유출로 제재". 우연히 비슷하거나 같은 기사를 인용했다면 이유를 적고 "제재하지 않음" |
| 〃 | **비정상 열람**: 10분 동안 화면을 연 횟수, 열람 간격, 탐지 이유 | 퍼진 캡처의 워터마크 등 다른 근거가 있으면 "제재하기"(대량 유출). 빠르게 넘겨 읽은 것이면 "제재하지 않음" |
| 〃 › 워터마크로 열람자 찾기 | 캡처나 증거 이미지에 보이는 8자리 코드의 열람자 | "워터마크 일치를 근거로 이 회원 제재하기"를 누르면 탐지 결과로 남고 제재 화면으로 이동 |
| 회원 관리 (`/admin/members`) | **다중 계정 의심**: 같은 IP를 두 계정 이상이 쓴 기록. "번갈아 사용", "차단" 표시가 있는 것부터 확인 | 같은 사람이 맞다고 판단되면 관련된 **모든 계정**을 하나씩 제재(사건에서 제외). 휴대폰 데이터는 통신사가 IP를 돌려 쓰기도 하므로 표시만으로 판단하지 않음 |

- 제재하면 탐지 번호가 제재 기록에 근거로 남고, 탐지 결과는 '처리한 탐지 결과'로 옮겨집니다. 복사 글은 올린 사람을 제재한 뒤에도 거기서 원본 열람자를 다시 볼 수 있습니다.
- 기각한 이유는 기록으로 남습니다. 같은 열람은 다시 탐지되지 않습니다.
- 탐지 기준값은 `src/domain/leak.ts`에 있습니다. 오탐이 많으면 사건 규모에 맞게 고칠 수 있습니다 (05 자동 탐지 기준).

게시한 뒤에는 사건 내용과 기간을 고칠 수 없습니다 (05). 서버 장애로 마감을 놓친 경우 외에는 기간을 바꾸지 마세요. 2심의 단계 기간은 게시 전에 정한 기간을 그대로 다시 씁니다.

## 5. 사이트 폐쇄와 개인정보 파기

사건이 폐기되거나 판결이 확정되면 `/admin/case`에 사이트 폐쇄 영역이 나타납니다.

1. **폐쇄 일시 공지**: 폐쇄 일시(최소 하루 뒤)와 종료 안내 페이지에 남길 결과 요약을 입력합니다. 결과 요약에는 닉네임이나 글 내용을 넣지 마세요. 공지가 올라가고 모든 회원에게 알림과 이메일이 갑니다.
2. **폐쇄 실행**: 공지한 일시가 지나면 실행합니다. 상태가 '사이트 폐쇄'로 바뀌고 회원 정보와 작성한 글, 증거 이미지 파일이 모두 파기됩니다. 운영자 계정도 함께 사라지고, 모든 주소에서 종료 안내 페이지만 보입니다.
3. **파기 확인**: 서버에서 파기를 한 번 더 실행해 남은 회원이 0명인지 확인합니다.

```bash
docker compose run --rm worker npm run purge -- --confirm
```

4. **남은 파기 작업** (폐쇄 실행 후 5일 이내, 05 개인정보 정책)
   - 서버의 `.env`에서 `IP_HASH_SECRET`과 `SESSION_SECRET`을 지웁니다.
   - DB 백업본(과 `uploads` 볼륨 백업본)이 있다면 함께 파기합니다.
   - 종료 안내 페이지를 계속 둘 필요가 없다면 서버를 내리고 DB 볼륨도 지웁니다.

```bash
docker compose down -v
```

## 6. 문제 해결

| 증상 | 확인할 것 |
|---|---|
| 모든 사람이 "이 네트워크에서는 이미 다른 계정이 이용 중"으로 가입이 막힘 | Caddy 앞에 다른 프록시가 있어 모두 같은 IP로 보이는 경우. 2번의 IP 규칙 주의 참고 |
| "접속 IP를 확인할 수 없습니다" | `CLIENT_IP_HEADER`가 Caddy가 넣는 헤더(`x-real-ip`)와 같은지 |
| 단계가 마감 후에도 넘어가지 않음 | 워커 로그 확인. 사건 페이지나 관리자 화면을 열면 넘어가지만, 실제 운영에서는 워커가 필요 |
| 이메일이 오지 않음 | SMTP 설정. 인증 코드는 바로 보내고, 서명·평결 요청, 2심 개시·승인 안내, 폐쇄 안내는 워커가 1분마다 보냄 |
| 이미지를 올리면 "jpg, png, webp 파일만" | 확장자만 바꾼 파일이거나 손상된 이미지. 형식은 파일 내용으로 확인함 |
| 이미지가 깨져 보임 | `uploads` 볼륨이 앱 컨테이너에 연결되어 있는지(`docker compose config`), 서버를 옮기며 볼륨을 빠뜨리지 않았는지 |
| 자동 탐지 결과가 너무 많음 | 탐지만으로는 제재되지 않으므로 기각해도 됨. 계속 많으면 `src/domain/leak.ts`의 기준값 조정 |
| AI 추천이 "AI 추천 없음" | `AI_PROVIDER`와 키 설정, 워커 로그의 AI 오류. 관리자 화면의 "AI 추천 받기"로 다시 시도할 수 있음 |
